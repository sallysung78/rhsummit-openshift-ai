# AgentOps 모듈 5 — 에이전트·LLM 평가 (Evals) 학습 노트

> 원문: <https://rhpds.github.io/agentops-in-prod-showroom/modules/07-module-05-evals.html>
> Red Hat Demo Platform의 *AgentOps in Production* 랩 자료입니다. 이 문서는 개념과
> 실습 의도를 한국어로 정리한 **요약 노트**이며, 단계별 절차와 코드는 원문을 보세요.

## 이 모듈이 답하려는 질문

관측(observability)은 **시스템이 도는가**를 알려주고, 평가(evaluation)는
**에이전트가 잘 하고 있는가**를 알려줍니다. 둘은 다른 층위입니다.

랩이 드는 예가 설득력 있습니다 — 하루 1만 건을 처리하는 모기지 심사 에이전트의
오류율이 1%라면 하루 100건이 틀립니다. 관측만으로는 응답이 200 OK로 잘 나갔다는 것만
보이고, **내용이 틀렸다는 사실은 몇 주 뒤 고객이 항의할 때까지 드러나지 않습니다.**
규제 산업이면 그 몇 주가 치명적입니다.

## 학습 목표

- OpenShift AI에서 Jupyter 워크벤치 기동
- MLflow Prompt Registry에 버전이 붙은 프롬프트 등록
- 입력과 기대 출력으로 구성된 평가 데이터셋 작성
- 결정론적 스코어러와 LLM-as-a-Judge 평가를 실제 에이전트에 대해 실행
- MLflow UI에서 결과와 트레이스별 평가 분석

## 선행 조건

| | |
|---|---|
| 플랫폼 | Red Hat OpenShift AI, 관리형 Jupyter 워크벤치 |
| LLM | 엔드포인트 base URL과 API 키 |
| 추적 | MLflow 트래킹 서버 접근 |
| 코드 | mortgage-ai 애플리케이션 저장소 |

예제 애플리케이션은 **Fed Aura Capital**이라는 가상의 모기지 회사입니다.

## 핵심 개념

### Prompt Registry — 프롬프트를 위한 git

MLflow의 Prompt Registry는 **시스템 프롬프트의 버전 관리**입니다. 랩은 이를
"프롬프트를 위한 git"이라고 표현합니다.

중요한 건 단순 이력 보관이 아니라 **평가 결과가 그것을 만들어낸 프롬프트 버전에
자동으로 연결된다**는 점입니다. 품질이 떨어졌을 때 "어느 프롬프트 수정이 원인인가"를
추적할 수 있고, 되돌릴 수 있습니다.

### 결정론적 스코어러 — 싸고 빠른 1차 방어선

LLM 호출 없이 규칙으로 판정합니다.

| 스코어러 | 확인하는 것 | 잡아내는 실패 |
|---|---|---|
| `contains_expected` | 기대 키워드 포함 여부 (예: FHA 대출 질문에 "FHA"가 나오는가) | 엉뚱한 주제로 새는 응답 |
| `has_numeric_result` | 금액·비율 같은 수치 존재 여부 | 계산해야 할 질문에 말만 하는 응답 |
| `response_length` | 최소 길이 (50자 이상) | 빈 응답, 잘린 응답 |

명백한 회귀를 잡는 용도입니다. 빠르고 비용이 0이므로 먼저 돌립니다.

### LLM-as-a-Judge — 미묘한 실패를 잡는 2차 방어선

LLM이 다른 LLM의 출력을 평가합니다. 이 랩에서 쓰는 판정자 5종:

| 판정자 | 평가하는 것 |
|---|---|
| `ToolCallCorrectness` | 적절한 도구를 호출했는가 |
| `ToolCallEfficiency` | 도구 사용이 최소한이고 논리적인가 |
| `RelevanceToQuery` | 사용자가 실제로 물은 것에 답했는가 |
| `Safety` | 안전하고 맥락에 맞는가 |
| `Guidelines` | 업무 규칙 준수 (금리 보장 금지, 전문적 어조 등) |

랩에 따르면 키워드 검사만 할 때보다 **17% 더 많은 품질 문제**를 찾아냈습니다.
키워드는 통과하지만 실제로는 쓸모없는 답 — 그게 LLM 판정자의 영역입니다.

> 두 계층을 함께 쓰는 이유가 여기 있습니다. 결정론적 스코어러는 공짜지만 얕고,
> LLM 판정자는 깊지만 호출 비용과 지연이 붙습니다.

### 프롬프트-트레이스 연결

모든 평가 트레이스가 그것을 생성한 프롬프트 버전에 자동으로 묶입니다.
품질 지표가 떨어졌을 때 며칠치 데이터를 수동으로 대조할 필요 없이 **어느 버전이
원인인지 바로 나옵니다.** 새 버전을 등록하면 이후 평가는 자동으로 새 버전을 기준으로
기록됩니다.

### 내부 루프와 외부 루프

| | |
|---|---|
| **내부 루프** (이 모듈) | 개발 중 수동 평가. Jupyter에서 프롬프트를 바꿔가며 돌리고 결과를 보고 반복 |
| **외부 루프** (모듈 6) | 파이프라인으로 자동화. 일정이나 트리거로 돌면서 회귀를 상시 탐지 |

이 모듈은 내부 루프만 다룹니다. 손으로 빠르게 돌려보는 단계입니다.

## 실습 구성 (7개)

| | 내용 |
|---|---|
| 1 | Jupyter 워크벤치 기동 |
| 2 | 저장소 클론, 평가 노트북 열기 |
| 3 | MLflow Prompt Registry에 프롬프트 등록 |
| 4 | 평가 데이터셋 작성 (입력 + 기대 출력) |
| 5 | 단순 평가 실행 — 스코어러 정의, predictor 연결, MLflow에서 결과 확인 |
| 6 | LLM-as-a-Judge 평가 실행 |
| 7 | 프롬프트-트레이스 연결 확인 |

전체 20~30분 정도 걸립니다.

## 우리 환경과의 관계

우리 클러스터(OpenShift AI 3.5)에는 `modelregistry`가 켜져 있고 `default-modelregistry`가
Ready 상태이지만, **이 랩이 쓰는 MLflow는 별개입니다.** RHOAI 3.x의 DSC에
`mlflowoperator` 컴포넌트가 있으나 현재 `Removed`로 꺼 둔 상태입니다.

이 랩을 우리 환경에서 재현하려면 `manifests/32-dsc.yaml`에서 `mlflowoperator`를
`Managed`로 바꾸거나, 랩이 제공하는 MLflow 인스턴스를 써야 합니다.

## 정리

평가는 "모델이 좋은가"를 재는 벤치마크가 아니라 **"내 프롬프트를 바꿨을 때 뭔가
망가졌는가"를 재는 회귀 테스트**에 가깝습니다. 소프트웨어의 단위 테스트가 하는 역할을
프롬프트와 에이전트에 대해 하는 것이고, 그래서 버전 관리(Prompt Registry)와
자동화(모듈 6)가 따라붙습니다.
