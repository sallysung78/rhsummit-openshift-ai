# 2026-09-26 작업 기록

MLflow 연동, 35B 비교 벤치마크, 모델 반입 검증 파이프라인 구축. 이 문서는 **무엇을
했는지**가 아니라 **무엇에 걸렸고 어떻게 알아냈는지**를 남깁니다. 같은 함정을 다시
밟지 않는 것이 목적입니다.

## 1. MLflow 연동

### 증상

`MLflow` CR 이 이 상태에서 멈췄습니다.

```
[Available=False]  reason=MigrationRunning
  Waiting for migration Job mlflow-mg-3140-g1 to finish because
  status.version is empty during bootstrap
```

CR 을 만든 네임스페이스에서 **Job 도 PVC 도 이벤트도 없었습니다.** 오퍼레이터는
5분마다 "Migration requested" 만 반복하고, 로그의 `namespace` 필드는 비어 있었습니다.
이 조합 때문에 "오퍼레이터가 Job 을 아예 만들지 않는다"고 잘못 판단했습니다.

### 진짜 원인

`MLflow` CRD 는 **클러스터 범위**입니다.

```bash
oc get crd mlflows.mlflow.opendatahub.io -o jsonpath='{.spec.scope}'   # → Cluster
```

`metadata.namespace` 는 무시되고 오퍼레이터는 `redhat-ods-applications` 에 배포합니다.
Job·PVC·이벤트가 전부 거기 있었고, 실패 이유도 거기에만 있었습니다.

```
Failed  mlflow-mg-3140-g1-bjkm8  Error: secret "s3-models" not found
```

`spec.envFrom` 이 참조하는 S3 시크릿을 모델 프로젝트에만 만들어 둔 것이 원인입니다.
시크릿을 `redhat-ods-applications` 로 복사하니 Job 이 **자동 재시도로** 통과하고
CR 이 `Migration=MigrationSucceeded`, `Available=True`, `version: 3.14.0` 이 됐습니다.

> **교훈**: 클러스터 범위 CRD 의 부작용은 "내가 보는 곳에 아무것도 없다"는 형태로
> 나타납니다. CR 이 조용히 멈췄으면 **CRD scope 를 먼저 확인**하세요.

### EvalHub 가 MLflow 를 못 찾던 이유

TrustyAI 오퍼레이터는 `MLFLOW_CA_CERT_PATH`, `MLFLOW_TOKEN_PATH`,
`MLFLOW_WORKSPACE` 는 자동 주입하지만 **`MLFLOW_TRACKING_URI` 는 넣지 않습니다.**
없으면 조용히 건너뜁니다.

```
warn  MLFlow tracking URI is not set, skipping MLFlow client creation
```

EvalHub CR 의 `spec.env` 에 직접 넣어야 합니다. 값은 MLflow CR 의
`status.address.url` 입니다.

**`oc rollout restart` 로는 안 됩니다.** 오퍼레이터가 어노테이션을 되돌립니다 —
새 ReplicaSet 은 만들어지지만 0 으로 유지되고 기존 파드가 그대로 살아 있습니다.
CR 을 고쳐서 오퍼레이터가 재배포하게 해야 합니다.

성공하면 기동 로그가 이렇게 바뀝니다.

```
info  MLflow workspace support probed   workspaces_enabled=true
info  MLflow workspace configured       workspace=<PROJECT>
info  MLFlow tracking enabled
info  MLFlow request successful  GET /version  status=200
```

### 확인 방법과 한계

MLflow API 는 **워크스페이스 컨텍스트**를 요구합니다. 헤더 없이 호출하면
`Workspace context is required for this request.` 가 납니다. 워크스페이스 이름은
네임스페이스와 같습니다.

```bash
curl -H "X-MLflow-Workspace: <PROJECT>" -H "Authorization: Bearer $TOKEN" \
     -X POST .../api/2.0/mlflow/experiments/search -d '{"max_results":10}'
```

> ⚠️ **기대치를 낮춰 두세요.** EvalHub 3.5 는 run 을 만들고
> `evaluation-card.json` 아티팩트 **하나만** 올립니다. MLflow metric 으로는
> 기록하지 않고 run 상태도 `RUNNING` 으로 남습니다. 대시보드에서 그래프 비교를
> 보여줄 계획이었다면 어긋납니다. 숫자는 카드 JSON 안에 있습니다.

UI 는 별도 Route 가 없고 대시보드에 **module federation 으로 임베드**되어 있습니다
(`federation-config` 에 `mlflow`, `mlflowEmbedded`). `https://rh-ai.apps.<도메인>/mlflow`
로 열립니다. 서버 인자의 `--static-prefix=/mlflow` 가 그 이유입니다.

## 2. 성능 측정의 재현성 — 그리고 `parameters` 는 무시된다

앞서 같은 모델에서 248 tok/s 와 36.9 tok/s 라는 크게 다른 수치를 얻어, 측정을
믿을 수 있는지부터 확인했습니다.

**같은 조건 두 번 → 거의 완전히 일치.**

| 회차 | output_tok/s | mean_ttft_ms | requests/s |
|---|---|---|---|
| 1회 | 36.8749 | 104.956 | 0.2833333 |
| 2회 | 36.8705 | 104.969 | 0.2833333 |

편차 0.01%. 측정 자체는 재현됩니다.

**그다음 `rate=8`, `max_seconds=60` 으로 바꿔서 다시 측정.**

| 조건 | output_tok/s | mean_ttft_ms | requests/s |
|---|---|---|---|
| rate=2, 120s | 36.8705 | 104.97 | 0.2833333 |
| rate=8, 60s | 36.8898 | 105.53 | 0.2833333 |

**메트릭이 동일합니다.** `requests_per_second` 가 소수점 7자리까지 같습니다.

처음에는 "`parameters` 가 무시된다"고 결론지었는데, **정확하지 않았습니다.**
나중에 어댑터 로그를 보니 값은 그대로 전달됩니다.

```
Running command: guidellm benchmark --target http://localhost:8080/v1   --profile sweep --rate 2 --max-seconds 120   --data prompt_tokens=256,output_tokens=128 ...
```

진짜 원인은 **`--profile sweep` 이 고정**이라는 것입니다. benchmark id 를 `constant`
로 줘도 프로파일은 sweep 이고, sweep 은 `synchronous` → `throughput` 을 돌려
**부하율을 스스로 탐색**합니다. 그래서 `--rate` 가 결과에 영향을 주지 못합니다.

```
strategy_types=['synchronous','throughput']   sweep_size=2
constraints={'max_seconds': 120.0}
```

`--max-seconds` 는 각 단계의 제한으로 실제로 쓰입니다(그래서 rate=8 실행이 더
오래 걸렸습니다). 영향이 없는 것은 `--rate` 쪽입니다.

> **정리**: EvalHub 경유로는 "고정 부하율" 측정을 요청할 수 없습니다. 대신 워크로드가
> 항상 같으므로 **모델 간 비교에는 유리합니다.** 앞서 나온 248 tok/s 는 GuideLLM CLI
> 를 직접 호출한 결과라 워크로드가 다릅니다 — **두 수치를 나란히 인용하면 안 됩니다.**

## 3. 모델 반입 검증 파이프라인

설계는 이전에 세웠고 이번에 구현했습니다. GPU 1장이라는 제약이 구조를 지배합니다.

```
preflight → release(기준 내림) → deploy(후보) → smoke → measure
          → gate → (통과: promote) → teardown(후보 내림 + 기준 복원)
```

`teardown` 은 `dsl.ExitHandler` 로 붙여 **통과/기각 무관하게 항상** 실행됩니다.
빼면 파이프라인이 유일한 GPU를 잡은 채 끝나 수동 데모가 막힙니다.

### 함정 ①: MariaDB 가 latin1 이라 한국어를 못 쓴다

가장 오래 걸린 문제입니다. 업로드하면 이것만 돌아옵니다.

```json
{"error_message":"Failed to create a pipeline and a pipeline version", ...}
```

에러 본문에는 Go 스택트레이스만 있고 원인이 없습니다. **`ds-pipeline-dspa` 파드
로그**에 진짜 원인이 있었습니다.

```
InternalServerError: Failed to insert a new pipeline:
Error 1366 (22007): Incorrect string value: '\xEB\xAA\xA8\xEB\x8D\xB8...'
```

`\xEB\xAA\xA8\xEB\x8D\xB8` 은 "모델" 입니다. 컬럼 charset 을 확인했습니다.

```
pipelines          Description    latin1  latin1_swedish_ci
pipeline_versions  PipelineSpec   latin1  latin1_swedish_ci
```

**KFP 는 각 컴포넌트의 소스 코드를 그대로 스펙에 박아 넣습니다.** 따라서 주석이든
로그 메시지든 파일 안에 한국어가 하나라도 있으면 업로드가 실패합니다. 업로드 시
넘기는 `name`/`description` 쿼리 파라미터도 마찬가지입니다 — 스펙을 다 영문으로
바꾼 뒤에도 실패했고, 남은 원인이 제 업로드 스크립트의 한국어 설명이었습니다.

대응: **파이프라인 코드는 영문으로 쓰고**, 한국어 설명은 별도 문서에 둡니다.
그리고 컴파일 직후 ASCII 검사를 넣어 서버에서 불투명한 에러를 받는 대신
컴파일 시점에 막습니다.

```python
raw = open(out, "rb").read()
try:
    raw.decode("ascii")
except UnicodeDecodeError as e:
    raise SystemExit("non-ASCII at offset %d — DSPA MariaDB is latin1" % e.start)
```

> MariaDB 를 utf8mb4 로 ALTER 하는 대안도 있지만 DSPA 가 관리하는 DB 의 스키마를
> 바꾸는 일이라 재생성 시 되돌아갈 수 있습니다. 코드를 ASCII 로 두는 쪽이 어디서든
> 동작합니다.

### 함정 ②: ExitHandler 의 exit task 는 다른 태스크에 의존할 수 없다

`release_gpu` 가 삭제한 스펙을 돌려주고 `teardown` 이 그걸로 복원하는 게 자연스럽지만
KFP 가 막습니다.

```
ValueError: exit_task cannot depend on any other tasks.
```

기준 모델 스펙을 **파이프라인 파라미터**로 받아 해결했습니다.

### 함정 ③: 출력을 안 쓰면 순서가 사라진다

②의 결과로 `deploy_model` 이 `release_gpu` 의 출력을 더는 참조하지 않게 됩니다.
그러면 KFP 가 둘을 **병렬로** 돌립니다. `dep.after(rel)` 을 명시해야 합니다.
빠뜨리면 기준 모델이 GPU를 잡은 상태로 후보 배포가 시작되고 후보 파드가 Pending 에서
영원히 멈춥니다. 데이터 의존성이 사라지면 실행 순서도 사라진다는 것을 기억하세요.

### 함정 ④: 업로드 토큰

kubeconfig 가 admin 클라이언트 인증서를 쓰면 `oc whoami -t` 가 실패합니다.

```
error: no token is currently in use for this session
```

DSPA API 는 Bearer 토큰만 받습니다. 전용 SA 를 만들고
`ds-pipeline-user-access-dspa` 롤을 묶어 `oc create token` 으로 발급합니다.
그 롤의 정체는 `datasciencepipelinesapplications/api` 라는 가상 리소스 권한입니다.

### RBAC — 부족한 건 nodes 하나뿐

`pipeline-runner-dspa` 는 `serving.kserve.io/inferenceservices` 에 대한
create/get/list/patch/delete 를 **이미** 갖고 있습니다(DSPA 가 만들어 줍니다).
`preflight` 의 nodes 읽기만 없고, nodes 는 클러스터 범위라 ClusterRole 이 필요합니다.
읽기 전용, 대상은 nodes 하나로 한정했습니다.

### TLS CA 를 볼륨 마운트 없이 얻기

EvalHub Service 인증서는 service-ca 가 서명합니다. 검증용 CA 는 OpenShift 가
**모든 네임스페이스에 자동 주입**하는 `openshift-service-ca.crt` configmap 에 있습니다.
컴포넌트 안에서 API 로 읽어 파일로 쓰면 `kfp-kubernetes` 확장(볼륨 마운트)이 필요
없고 `verify=False` 로 도망갈 이유도 없습니다.

### 이미지 풀 실패는 재시도로 낫는다

첫 실행에서 컴포넌트 파드가 `ErrImagePull` 로 떨어졌습니다.

```
Failed to pull image "registry.access.redhat.com/ubi9/python-311:latest":
... happened during read: unexpected EOF (while reconnecting: ... cdn01.quay.io ...)
```

태그 오류나 디스크 부족이 아니라 **CDN 전송이 끊긴 것**입니다(노드 DiskPressure 는
전부 False). kubelet 백오프 재시도로 통과했습니다. 잘못된 이미지 이름이라고
결론 내리기 전에 메시지 전문을 읽으세요.

## 4. 세션을 다른 곳에서 이어받기

작업 폴더에 `CLAUDE.md` 를 두면 그 폴더에서 새 세션을 열 때 자동으로 읽힙니다.
상시 지시(자동 정지된 환경 복구, 영문 번역), 자격증명 위치, 진행 상황, 반복해서
다시 걸렸던 함정을 한 장에 모았습니다.

주의할 점 두 가지입니다.

**복구에 필요한 파일은 커밋되지 않습니다.** `cluster/auth/kubeconfig`(2036년까지
유효한 admin 인증서), `ACCESS.local.md`, `aws-creds`, `s3-creds.env`, `ssh/` 는 모두
로컬 전용입니다. 의도한 것이고, 그래서 **GitHub만 clone 해서는 클러스터에 붙을 수
없습니다.** 다른 노트북에서 작업하려면 로컬 자격증명 동기가 끝났는지 먼저 확인하세요.

**폴더를 지정하지 않고 세션을 열면** 앱이 만든 임시 작업공간에서 돌고, 세션이 사라지면
그 폴더도 지워집니다. 프로젝트 작업은 실제 폴더를 지정해서 하세요.
