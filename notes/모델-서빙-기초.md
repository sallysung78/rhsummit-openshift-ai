# 모델 서빙 기초 — OpenShift AI

> RHOAI 3.4 교육 자료(모델 서빙 워크플로·아키텍처, 런타임 호환성)를 한국어로 요약한
> 노트입니다. 우리 클러스터는 3.5.1이지만 구조는 같습니다.

## 모델 서빙이 뭔가요

학습이 끝난 AI 모델은 **숫자가 잔뜩 든 파일**입니다. 파일만으로는 아무 일도 일어나지
않습니다. 그 파일을 메모리에 올려두고 질문을 받아 답해주는 프로그램이 필요한데,
이 과정 전체를 **모델 서빙**이라고 합니다.

> 음악 파일과 재생기의 관계입니다. mp3만 있으면 소리가 안 나고, 재생기가 있어야 들립니다.

서빙의 결과물은 **API 엔드포인트**입니다. 앱이 HTTP로 질문을 보내면 답이 돌아옵니다.
그 순간부터 모델은 "파일"이 아니라 "서비스"가 됩니다.

## 서빙 플랫폼이 대신 해주는 일

모델을 그냥 띄우는 것과 *운영*하는 것은 다릅니다. 실제로 필요한 것들:

| | |
|---|---|
| **확장** | 사용자가 몰리면 복제본을 늘리고, 한가하면 줄임 |
| **실시간 응답** | 챗봇·사기탐지처럼 즉답이 필요한 경우 |
| **배치 처리** | 한 번에 몰아서 처리하면 효율이 좋은 경우 (추천, 분석) |
| **분산 추론** | 모델이 GPU 하나에 안 들어갈 때 여러 장에 쪼개서 (llm-d) |
| **모니터링** | 응답 속도, 자원 사용량, 그리고 **품질 저하(드리프트)** 감지 |
| **버전 관리** | 어느 버전이 운영에 떠 있는지 추적 (모델 레지스트리) |
| **보안** | 접근 제어, 통신 암호화, 토큰 인증 |

OpenShift AI는 이걸 **KServe** 위에 얹어서 제공합니다. 쿠버네티스가 원래 잘하는
일(스케줄링·확장·라우팅)을 모델에 그대로 적용하는 방식입니다.

## 전체 흐름 6단계

```
1. 모델 학습 또는 카탈로그에서 선택
2. 스토리지에 저장          (S3 / OCI 이미지 / URI)
3. 모델 레지스트리에 등록    ← 여기가 관문. 버전·출처·메타데이터 기록
4. 배포                    ← 런타임·자원·복제본 수를 정하면 서버가 뜸
5. 추론 요청 처리           HTTP REST 또는 gRPC
6. 모니터링                문제 발견 → 재학습 → 1번으로
```

**3번(레지스트리)이 중요한 이유**: 스토리지에서 바로 배포할 수도 있지만, 그러면
"지금 운영에 뭐가 떠 있는지, 누가 올렸는지, 어느 버전인지"를 아무도 모릅니다.
레지스트리는 그 거버넌스 지점입니다.

## 구조 — 기억할 리소스는 두 개뿐

| 리소스 | 역할 | 비유 |
|---|---|---|
| **ServingRuntime** | 모델을 *어떻게* 실행할지 — 컨테이너 이미지, 지원 포맷, 권장 가속기 | **재생기** |
| **InferenceService** | *어떤* 모델을 그 런타임으로 띄울지 — 모델 위치, 자원, 복제본 수 | **재생 목록** |

`InferenceService`를 만들면 KServe가 알아서 Deployment·Service·Route를 만듭니다.

### InferenceService에서 실제로 정하는 것

```yaml
spec:
  predictor:
    minReplicas: 1 / maxReplicas: 1     # 복제본 수
    model:
      modelFormat: { name: vLLM }        # 모델 포맷
      runtime: vllm-runtime              # 어느 런타임을 쓸지
      resources:
        limits: { cpu: '6', memory: 24Gi, nvidia.com/gpu: '1' }
      storage:
        key: aws-connection-my-storage   # 스토리지 연결 이름
        path: models/granite-7b-instruct/
    tolerations:                          # 테인트 걸린 GPU 노드에 들어가기 위한 허가증
      - key: nvidia.com/gpu
        effect: NoSchedule
        operator: Exists
```

### 배포하면 실제로 생기는 것

```
[앱] --HTTPS--> [Route] --> [Service] --> [Pod]
                                            ├─ kserve-container   모델 로드 + 추론 (항상)
                                            ├─ modelcar           OCI 저장소 쓸 때만
                                            └─ kube-rbac-proxy    토큰 인증 켤 때만
```

S3나 PVC를 쓰면 `kserve-container` 하나뿐입니다. OCI 이미지를 쓸 때만 사이드카가 붙습니다.

> **배포 모드는 이제 하나입니다.** 예전에 있던 Serverless 모드는 RHOAI 2.25부터
> 폐기(deprecated)됐고 **raw deployment**만 씁니다. 그래서 Service Mesh나 Serverless
> 오퍼레이터가 더 이상 필요 없습니다.

## 런타임 고르기

**모델 종류에 맞는 런타임을 골라야 합니다.** mp3를 동영상 재생기로 못 여는 것과 같습니다.

| 런타임 | 지원 모델 | 가속기 | API |
|---|---|---|---|
| **vLLM** | LLM (Safetensors) | NVIDIA·AMD·Intel Gaudi·IBM Spyre·CPU | OpenAI 호환 REST |
| **OpenVINO Model Server** | ONNX, TensorFlow, PyTorch, OpenVINO IR 등 | Intel CPU/GPU | REST |
| **MLServer** | scikit-learn, XGBoost, LightGBM | **CPU 전용** | REST |
| Caikit-TGIS / Caikit Standalone | Caikit 포맷 (텍스트 생성 / 임베딩) | — | REST, gRPC |

NVIDIA Triton 등은 *tested and verified* 범주로, 호환성은 검증되지만 **Red Hat 지원
대상이 아닙니다.**

### 주의할 점 두 가지

**vLLM은 GPU 제조사별 변형이 따로 있습니다.** NVIDIA 클러스터에 AMD 변형을 고르면
배포가 실패합니다. 우리는 **`vLLM NVIDIA GPU ServingRuntime for KServe`** 입니다.

**하드웨어 프로파일을 잘못 고르면 늦게 실패합니다.** CPU 프로파일을 GPU 런타임에
붙여도 스케줄링은 됩니다 — 대신 vLLM이 기동하다가 GPU를 못 찾고 죽습니다. 원인이
한참 뒤에 드러나는 유형입니다.

### 런타임은 Template으로 들어 있습니다

사전 설치 런타임은 네임스페이스의 CR이 아니라 `redhat-ods-applications`의
**OpenShift Template**입니다. 배포하는 순간 인스턴스화되어 *내 프로젝트에* 실제
ServingRuntime CR이 생깁니다.

```bash
oc get template -n redhat-ods-applications
```

관리 위치: **Settings → Model resources and operations → Serving runtimes**

## 모델을 어디에 둘까

| 방식 | 첫 기동 | 재기동 | 잘 맞는 경우 |
|---|---|---|---|
| **S3** | 보통 (매번 다운로드) | 보통 | 주기적 재학습 모델 |
| **OCI 이미지** | 느릴 수 있음 | **빠름** (레이어 캐시) | 지연에 민감한 운영 |
| **PVC** | 빠름 | 빠름 | 다중 노드 |
| URI | — | — | 빠른 프로토타이핑 |

## 양자화 — 모델 다이어트

원본 LLM은 GPU에 안 들어갈 만큼 큽니다. **숫자의 정밀도를 낮춰 용량을 줄이는 것**이
양자화입니다. 사진을 JPG로 압축하는 것과 비슷합니다 — 용량은 확 줄고 품질은 조금
떨어집니다.

| 포맷 | 하드웨어 제약 |
|---|---|
| **AWQ / GPTQ** (4비트) | **대부분의 가속기** — 가장 무난 |
| INT8 W8A8 | NVIDIA Turing~Hopper (Blackwell 불가) |
| INT4 W4A16 | Ampere 이상 |
| FP8 W8A8 | **Ada Lovelace/Hopper**, AMD CDNA3, Gaudi |
| NVFP4 | Blackwell 전용 |

효과 예시: Qwen3 32B가 60 GB대 → **18 GB**로 줄어 48 GB GPU에 들어갑니다.

## 우리 환경에 대입

| 항목 | 값 |
|---|---|
| 런타임 | `vLLM NVIDIA GPU ServingRuntime for KServe` |
| 하드웨어 프로파일 | `NVIDIA L40S (1 x 48GB)` |
| 스토리지 | S3 (`s3://<INFRA_ID>-models`) |
| 모델 | Qwen3-8B-AWQ (5.7 GiB) / Qwen3-32B-AWQ (18.0 GiB) |
| 배포 모드 | raw deployment |

두 가지 덧붙이면:

**우리 L40S는 Ada Lovelace라 FP8도 가능합니다.** 교육 자료의 A100(Ampere) 예제는
FP8이 안 되지만 우리는 됩니다. 다만 데모에는 지금 쓰는 AWQ가 가장 안전합니다.

**하드웨어 프로파일 경고가 우리에게 더 강하게 적용됩니다.** GPU 노드에
`nvidia.com/gpu=true:NoSchedule` 테인트가 걸려 있어서, 잘못 고르면 자료가 말하는
"기동 중 실패"보다 앞에서 — 아예 `Pending`으로 — 막힙니다.
