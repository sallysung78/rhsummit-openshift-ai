# AgentOps 모듈 6 — 개발에서 운영으로 학습 노트

> 원문: <https://rhpds.github.io/agentops-in-prod-showroom/modules/08-module-06-dev-to-production.html>
> Red Hat Demo Platform의 *AgentOps in Production* 랩 자료입니다. 이 문서는 개념과
> 실습 의도를 한국어로 정리한 **요약 노트**이며, 단계별 절차와 코드는 원문을 보세요.

## 이 모듈이 답하려는 질문

모듈 5에서 만든 평가는 **사람이 노트북을 열어 실행해야** 돌아갑니다. 그러면 바쁠 때
건너뛰고, 환경마다 결과가 달라지고, 프롬프트를 고친 사람이 평가를 안 돌리면 아무도
모릅니다.

이 모듈은 그 평가를 **파이프라인으로 옮겨 자동으로 돌게** 만듭니다.

## 학습 목표

- 노트북 기반 워크플로와 자동화된 워크플로의 차이 이해
- 평가 로직을 컨테이너화된 파이프라인으로 배포
- 프롬프트 버전 비교와 회귀 탐지
- 평가 결과를 배포 전 품질 게이트로 사용

## 선행 조건

모듈 5를 마친 상태를 전제합니다 — 수동 평가, MLflow 연동, 스코어러 구현에 대한 이해.

## 내부 루프 → 외부 루프

| | 내부 루프 (모듈 5) | 외부 루프 (이 모듈) |
|---|---|---|
| 실행 | 개발자가 노트북에서 수동 | 일정·트리거로 자동 |
| 재현성 | 환경마다 다름 | 컨테이너로 고정 |
| 감사 | 실행 기록이 노트북에만 | 파이프라인 실행 이력으로 남음 |
| 용도 | 빠른 탐색과 반복 | 상시 회귀 탐지, 배포 전 검증 |

**평가 로직 자체는 같습니다.** 달라지는 것은 그것이 어디서, 누가 누르지 않아도
도는가입니다.

## 평가 파이프라인

Kubeflow Pipelines(OpenShift AI의 Data Science Pipelines) 위에 만들어지고,
네 단계를 순서대로 실행합니다:

1. MLflow 연결 설정
2. 평가 데이터셋 구성
3. 스코어러 실행
4. 결과 보고

이렇게 묶으면 노트북 없이도 돌고, 실행할 때마다 같은 결과가 나오고, 기록이 남습니다.

### 실행 시 지정하는 파라미터

| 파라미터 | 역할 |
|---|---|
| MLflow tracking URI / workspace | 결과를 어느 MLflow에 기록할지 |
| 에이전트 이름 | 어느 에이전트를 평가할지 |
| 데이터셋 이름 | 어떤 테스트 케이스로 평가할지 |
| experiment 이름 | MLflow에서 결과를 묶을 단위 |

## 핵심 실습 — 나쁜 프롬프트를 운영 전에 잡기

이 모듈에서 가장 볼 만한 부분입니다. 시나리오가 현실적입니다.

**개발자의 제안:** 시스템 프롬프트의 `TOOL USE (MANDATORY)`를 `TOOL USE (OPTIONAL)`로
바꾸면 도구 호출이 줄어 **응답이 빨라집니다.** 합리적으로 들립니다.

**스코어러가 드러낸 것:** 에이전트가 상품별 도구를 호출하지 않고 **일반 지식으로
답하기 시작합니다.** 결과적으로

- `contains_expected` 실패 — 상품 고유 정보(예: FHA 조건)가 응답에서 사라짐
- `has_numeric_result` 실패 — 실제 계산 대신 일반론

**판정:** 속도를 얻고 정확도를 잃었습니다. 순손실입니다.

실습은 이 과정을 그대로 밟습니다 — 수정된 프롬프트를 V2로 등록하고, MLflow에서 V1과
버전 비교를 하고, V2에 대해 평가를 돌리고, 두 결과를 나란히 놓고, 트레이스 단위로
어디서 틀렸는지 확인합니다.

> **이 실습의 진짜 교훈**: 사람 눈으로 응답 몇 개를 훑어봤다면 "빨라졌고 답도
> 그럴듯하다"로 통과시켰을 변경입니다. 스코어러가 없으면 이 회귀는 운영에 나간 뒤
> 고객이 잘못된 조건을 안내받고 나서야 드러납니다.

## 품질 게이트

평가 결과를 **배포 전 체크포인트**로 쓰는 것입니다. 프롬프트 버전을 기준선과 비교해
측정 가능한 회귀가 있으면 사용자에게 도달하기 전에 걸러냅니다.

소프트웨어에서 테스트가 깨지면 머지를 막는 것과 같은 구조를, 프롬프트에 대해
적용하는 것입니다.

## 실습 구성 (4개)

| | 내용 |
|---|---|
| 1 | 평가 파이프라인 임포트 (URL로) |
| 2 | 파라미터 설정 후 파이프라인 실행 |
| 3 | MLflow에서 자동 평가 결과 확인 |
| 4 | 회귀 탐지 — V2 등록 → 버전 비교 → 평가 → V1 대비 분석 → 트레이스별 확인 → 판정 |

세부 단계가 24개 이상이라 모듈 5보다 손이 많이 갑니다.

## 우리 환경과의 관계 — 여기가 중요합니다

**이 모듈을 우리 클러스터에서 돌리려면 파이프라인 서버가 먼저 필요합니다.**

우리 DSC에서 `aipipelines`는 `Managed`이고 `AIPipelinesReady=True`이지만, 그것은
오퍼레이터가 준비됐다는 뜻일 뿐입니다. 파이프라인은 **프로젝트(네임스페이스)마다
자기 서버**가 있어야 하고, 아직 어느 프로젝트에도 만들지 않았습니다.

RHOAI 대시보드에서 프로젝트 → Pipelines 탭에 가면 나오는

> *Configure a pipeline server — To create or use pipelines, you must first
> configure a pipeline server in this project.*

가 바로 그 이야기입니다.

파이프라인 서버의 `spec`에서 **필수는 `objectStorage` 하나**입니다. 이미 만들어 둔
버킷을 쓰면 됩니다:

| | |
|---|---|
| 버킷 | `s3://<INFRA_ID>-models` |
| basePath | `pipelines/` (프리픽스를 미리 만들어 두었습니다) |
| 연결 | `rhsummit` 프로젝트의 `S3 - model storage` |

데이터베이스는 지정하지 않으면 클러스터 안에 MariaDB가 자동으로 생성됩니다.

MLflow는 별개입니다 — DSC의 `mlflowoperator`가 현재 `Removed`이므로, 이 랩을 그대로
재현하려면 켜야 합니다.

## 정리

모듈 5가 "평가를 어떻게 만드는가"라면 이 모듈은 **"그 평가를 어떻게 잊지 않고 돌게
만드는가"**입니다. 자동화의 목적은 편의가 아니라, 사람이 건너뛸 수 있는 단계를
건너뛸 수 없게 만드는 데 있습니다.

`TOOL USE (OPTIONAL)` 예시가 그 점을 잘 보여줍니다 — 나쁜 의도도 무능도 아닌,
합리적으로 보이는 최적화가 품질을 깎아먹는 경우이고, 이런 건 자동 측정만이 잡습니다.
